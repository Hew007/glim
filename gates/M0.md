## 关于 0.6 的口径

WebView2 是 Chromium 多进程架构（本次稳定为 glim.exe + 6 个 msedgewebview2.exe），**直接把各进程 WorkingSet 相加会把共享页重复计入**，得到 342.5 MB 这种虚高数字。任务管理器显示的是「内存（活动的专用工作集）」，对应 `WorkingSetPrivate`，这也是门禁 0.6 的口径。两个数都列出：

| 口径 | 峰值 | 稳态 |
|---|---|---|
| 专用工作集（任务管理器口径，门禁用这个） | 74.9 MB | 71.0–71.8 MB |
| 各进程总工作集相加（含共享页重复，仅供参考） | 342.5 MB | ~339–342 MB |

子进程是按**父进程链**认定的，不是按命令行字符串匹配，避免把机器上其他应用的 WebView2 进程算进来。

**风险提示（不是放宽门禁，是如实标注）**：74.9 / 80 = 94%，只剩 6% 余量，而这还是「窗口只有四个空 div、没有任何网络与渲染内容」的状态。M1 接入流式请求和结果渲染后极可能顶破 80MB。建议在 M1 结束时重测 0.6，若超标则需要正面处理（例如面板长时间隐藏后释放 WebView2），不要留到 M4。

## 实现说明（请审核者重点看这几条）

### 1. `load_settings` 的返回值是 `Settings` 的超集

§4.1 写的是 `load_settings → Settings`。实际返回 `{ hotkey, hotkey_registered, hotkey_error }`：后两个是**运行时状态、不落盘**，settings.json 里只有 `hotkey`。这是为了在不新增 IPC 命令的前提下让前端知道热键是否注册失败（你选的方案就是「IPC 仅用 §4.1 已有的 load_settings / save_settings」）。命令名与语义都没动，只是返回结构多了两个只读字段。

同理 `save_settings` 声明返回 `()`，实现返回 `Result<(), String>` —— 成功时就是 `()`，失败时把「新热键注册失败」的原因抛给前端显示，以满足「不得静默失败」。

### 2. 显示/隐藏绕开了 tao，直接用 Win32

**踩到的坑**：tao 在改变窗口可见性时会拿它自己缓存的 `WindowFlags` **重写整个 ex-style**。实测 `show()` 之后 ex-style 从 `0x08000198` 变成 `0x00040118` —— `WS_EX_TOOLWINDOW` 和 `WS_EX_NOACTIVATE` 被抹掉，`WS_EX_APPWINDOW` 被加回来。而 Alt+Tab 的判定规则是「没有 TOOLWINDOW **或者** 有 APPWINDOW」，两个标志同时在等于 TOOLWINDOW 白加，门禁 0.2 直接失效。

现在 show 走 `SetWindowPos(HWND_TOPMOST, x, y, SWP_NOSIZE|SWP_NOACTIVATE|SWP_SHOWWINDOW)`（定位和显示一次完成，且不激活），hide 走 `ShowWindow(SW_HIDE)`。扩展样式在启动时打一次即可，不再被覆写。副作用是 Tauri 内部记录的可见性会与实际不一致，因此可见性以 Rust 侧自己的 `PanelState` 为准，不读 `window.is_visible()`。

### 3. Esc 的注册/注销必须在工作线程上做

**踩到的坑**：`global-hotkey` 在**主线程**创建隐藏窗口接收 `WM_HOTKEY`，`tauri-plugin-global-shortcut` 的事件分发是「持着 `shortcuts` 互斥锁同步调用 handler」，而 `register` / `unregister` 内部要拿同一把锁。在热键回调链里直接注册 Esc 就是同一线程重入非重入锁，**主线程当场死锁**，表现为第一次弹窗之后热键彻底失灵（第一版实现就是这样，20 次采样只采到 1 个）。

现在 Esc 的注册/注销走一条独立的 worker 线程 + channel，工作线程会阻塞到 handler 返回再拿锁，不会死锁。代价是 Esc 的生效比窗口出现晚几毫秒（异步下发），不影响门禁。

### 4. 冲突提示这一路径会临时摘掉 `WS_EX_NOACTIVATE`

`WS_EX_NOACTIVATE` 的窗口拿不到键盘焦点，那个用来改键的输入框会**根本打不进字**。所以启动时的热键冲突提示单独走 `show_focused()`：临时清掉 NOACTIVATE 并 `SetForegroundWindow`，`hide()` 时无条件还原。**热键正常路径不走这里**，全程保持不夺焦点（门禁 0.3 测的就是正常路径）。

### 5. 三处 PLAN.md 未写死、我按常识定的实现细节

请复核，不同意我就改：

- **`alwaysOnTop: true`**：不夺焦点的窗口如果不置顶，会直接出现在当前前台窗口**背后**，等于白弹。
- **`decorations: false`**：§4.3 规定固定宽 420px、高 180–560px，带标题栏会破坏这个尺寸约定，且「看完即走」的浮层不该有系统边框。这不算 UI 样式（没有任何 CSS）。
- **M0 窗口高度取 180px**：§4.3 的高度区间是 180–560 自适应，M0 没有内容，取区间下限。

### 6. 两个已知粗糙点（M0 范围内不修，登记在此）

- **改键输入框会被输入法干扰**：中文输入法开着时，往裸 `<input>` 里敲 `Ctrl+Alt+G` 会进入拼音合成态，候选条不关掉的话下一次点击会被输入法吃掉。门禁脚本里靠补一个 Enter 提交合成绕过。M3 的设置界面应该用**按键捕获控件**（监听 keydown 直接生成组合键），而不是让用户手打字符串，届时这个问题自然消失。
- **`save_settings` 先写盘再注册**：新热键注册失败时，失败的值已经落盘了。下次启动会再次触发冲突提示并显示这个值，路径是自洽的，但严格说应该注册成功后再落盘。M3 做设置界面时一并调整。

## 附：未列入门禁但 §4.3 要求、已实测通过的项

### 复核期间的产品缺陷：`was_down`（已修并验证）

点击外部轮询在面板隐藏期间无条件复位 `was_down`：

```rust
if !app.state::<PanelState>().is_visible() {
    was_down = false;      // 隐藏期间反复清零
    continue;
}
```

面板一变可见，第一次轮询就把「出现那一刻就已按住的左键」误判成新的按下沿并立即隐藏 —— **按住左键不放时按热键，面板一闪即消失**。审核者裁定在 M0 内修复（commit `ed350ad`），改为隐藏期间继续跟踪左键真实状态，只认真正的按下沿。

不在任何门禁的判定范围内（0.4 测的是「点击外部应关闭」，这是其反面），手工验证两步均通过：

- 按住左键不放 → 按 `Ctrl+Alt+D` → 面板弹出并保持可见，左键仍按住不消失。
- 松开左键 → 面板外单击 → 正常关闭（确认修复未破坏 0.4 的点击外部路径）。

### 两次失败的定性

**第一次（0.1c 第 17–20 轮 + 0.3）**：成对报错「show 后不可见」+「toggle 后仍可见」，即 toggle 相位整体反了一格。判定依据是采样数 —— 脚本在 0.1c 前清空日志，20 轮理应正好 20 个 show，实测 **21**；一次非热键触发的 hide 恰好产生「该轮 2 个采样 + 后续相位反转」，与观测完全吻合。当时脚本不输出 hide 原因，来源无法直接定性。`[0.3] 面板可见 = False` 是同一现象的下游（0.1c 结束时面板停在可见态，0.3 按热键变成 hide）；`[0.3] 记事本内容` 得到 hosts 文件首行则是无关的独立脚本缺陷。
