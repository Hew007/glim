## 1.2 未通过的详细数据与原因

### 实测分布

门禁本轮 10 个样本（`gemini-flash-lite-latest`）：

| 统计量 | 值 |
|---|---|
| 最小 | 790 ms |
| 中位 | 1816 ms |
| 最大 | 11567 ms |
| 阈值 | **1200 ms** |

10 个样本中有 3 个低于阈值，7 个高于。**分布是长尾而非稳定慢**：多数落在 1–2 秒，少数窜到 4–12 秒。

### 独立基准（绕开本程序全部代码）

用 `curl` 直接打同一个流式端点，`time_starttransfer` 即首字节延迟：

| 模型 | 样本 | 最小 | 中位 | 最大 | 成功率 |
|---|---|---|---|---|---|
| `gemini-flash-lite-latest` | 10 | 868 ms | 1375 ms | 13072 ms | 10/10 |
| `gemini-3.5-flash-lite` | 10 | 879 ms | 2323 ms | 9938 ms | 10/10 |
| `gemini-3.6-flash` | 4/10 | 19796 ms | 59331 ms | 61218 ms | **4/10** |

另有两轮 5 样本的早期基准，同为 `gemini-flash-lite-latest`：中位 **13930ms** 与 **1417ms**。**同一配置在不同时段的中位数可相差十倍。**

### 已排除的原因

| 假设 | 结论 | 依据 |
|---|---|---|
| 本程序的 SSE 解析慢 | **排除** | 日志三点打点显示 `[http]`（响应头）、`[first-byte]`（正文首字节）、`[first-chunk]`（解析出增量）三者相隔 **1ms**。全部等待发生在服务端响应之前 |
| 链路（代理）慢 | **排除为主因** | 同链路的 HTTP 400 往返固定约 **380–420ms**。这是固有开销，不解释 1.8–11.5 秒 |
| 换模型可解决 | **排除** | 三个模型横向对比，当前配置已是最好的一个。Google 在 404 中推荐的 `gemini-3.6-flash` 反而最差（成功率 4/10，中位近 60 秒） |
| 关闭模型「思考」可解决 | **排除** | `generationConfig.thinkingConfig.thinkingBudget = 0` 被服务端拒绝：`400 Request contains an invalid argument`。两个 flash-lite 模型均如此 |

### 已定位的原因

`gemini-3.6-flash` 的 503 响应体中出现 `"thoughtsTokenCount": 312 / 378 / 399` —— 翻译一句短句花费近 400 个思考 token，这解释了它 19–61 秒的延迟。当前所用的 flash-lite 响应中无此字段，故快得多，但**仍受免费层调度影响**：同一 prompt、同一模型、同一链路，延迟在 790ms 与 13072ms 之间跳变，且随时段整体漂移。

**结论：瓶颈在 Gemini 免费层的调度与跨境链路，不在本程序的实现。** §2.3 给的预算是「窗口 → 首字符 < 800ms」，而实测最快的一次是 790ms —— 即便一切顺利也只是刚好压线，没有余量。

### 不调整门禁

按 §10 第 7 条，「不得为了通过门禁而放宽门禁」。1200ms 这个数字未作任何改动，本报告如实记未通过。是否接受现状、调整指标、还是等 `OpenAICompatProvider`（已按 §9.5 记入变更记录，排在 M1 冻结之后）接入国内直连服务再测，由审核者裁定。

## 规格与现实的冲突（需裁定）

**§4.2 规定「15s 内无首字符」判 `Timeout`，而实测存在 17404ms 的成功响应。**

这意味着合法的慢响应会被程序自己掐断 —— 使用中出现的「15 秒内没有收到响应」有一部分并非失败，而是还差两秒就回来了。

这不是实现缺陷，是规格与实测环境不匹配。三条路：

1. 接受现状：慢到那个程度本来也不可用
2. 放宽超时（如 30s）：属改动 §4.2，须走 §9.5 变更记录
3. 等国内直连 Provider：届时 15s 绰绰有余

## 实现说明（请审核者重点看）

### 1. `request_id` 用单调递增计数器，而非 §4.3 字面的 UUID

两个理由：加 `uuid` crate 属 §1 清单外的第三方库（§10.1）；更重要的是**单调性让前端不必等 `start_request` 返回就能正确排序事件** —— 事件与 IPC 返回值走同一通道、不保证先后，UUID 无序时抢先到达的事件会因「id 不认识」被误丢。唯一性与「取消旧请求后不串台」两个目的都达到了。

### 2. `validate_api_key` 校验通过后顺手写入凭据管理器

§4.1 冻结了命令表，没有单独的「保存 Key」命令，而 §5.1 的引导流程本就是「粘贴 → 自动验证 → 成功即用」，验证与保存是同一个动作。Key 只进 Windows 凭据管理器，不进 settings.json。

### 3. Provider trait 拆成同步的两个方法

§4 写的是 `async fn translate(&self, req) -> Result<TextStream>`。实际拆成「构造请求」+「解析增量」，await 循环留在 `request.rs`：Rust 的 async trait 要么上 `async-trait`（§1 清单外），要么手写 Send 边界。抽象边界未变，M2 接 `OpenAICompatProvider` 照样只实现这两个方法。

### 4. Key 的输入方式：粘贴按钮，不是输入框

面板带 `WS_EX_NOACTIVATE`，拿不到键盘焦点。要让用户手打就必须临时摘掉该样式并抢焦点 —— 那会破坏已冻结的门禁 0.3（弹窗不夺焦点）。而取 Key 的路径本就是「在 AI Studio 复制 → 回来粘贴」，剪贴板里已经有了，点一下按钮即可，全程无需焦点。§5.1 的引导思路亦如此。

### 5. 首次启动落盘默认配置

`load` 读不到就静默返回默认值、从不写回，导致没改过热键的机器上 settings.json 根本不存在 —— 而 §4.3 规定模型串与端点写在配置里由用户调整，文件不存在时这条规定形同虚设。启动时补一次写入（仅当文件缺失）。

### 6. TLS 走 native-tls（Windows 上即系统 schannel）

复用操作系统的根证书库，不打包第二份证书，也避免 rustls 的 C 依赖（后者在交叉检查时需要 MSVC 的 `lib.exe`）。
